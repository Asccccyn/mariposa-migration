# mariposa · 给 GLM 的连续执行指令 v1.1

> 类型：执行方式补充，不是新的业务架构。  
> 适用：mariposa 工程执行包 v1.0；完整连续执行包 v1.1 已内置本文件。  
> 用户要求：一次交付完整任务，GLM 在现有授权内连续推进，不需要每个阶段询问“继续吗”；可充分使用现有额度，重视解耦。  
> 本文件没有运行应用、创建本地项目、审批真实记忆或扩大生产操作权限。

## 1. 本次总任务

你接到的是 mariposa **Phase 0–8 的连续实施任务**，不是只写方案、只做 Phase 0，或只完成 Phase 2 的小任务。

一次领取完整工程包，按依赖顺序持续完成实现、测试、修复、集成、文档与发布候选构建。每次阶段汇报只同步进度，不主动结束任务等待用户说“继续”。只要执行环境允许，且仍有已授权、依赖满足、可以推进的工作，就继续下一项。

“连续”指一次总任务下连续推进；不要求在一个模型回复、一份巨大补丁、一个 commit 或一个上下文窗口内做完。不得为追求一次性完成而跳过验证。

本文件只调整执行节奏，不放宽以下内容：业务要求、授权边界、原始验收预期、真正的身份与审批、旧生产隔离、外部服务副作用限制，以及文档中已声明的后续预留范围。

## 2. 阅读顺序与优先级

先读 `00_给GLM的开工指令.md` 和本文件，再读 `01_工程执行文档.md`、`04_决策记录与来源.md`、`02_验收用例.md`、`03_迁移与切换手册.md`、`contracts/`。

本文件在“是否等用户逐阶段确认”上优先；业务事实和验收要求仍以 v1.0 主文档及明确的新用户指令为准。旧 v0.4 仅为历史参考，不能恢复已被替换的规则。

两份规格出现真正矛盾时，记录定位、影响和临时阻塞；继续不受影响的模块。不能用本文件的“自动继续”来选择一个更宽松的权限规则。

## 3. 总体执行循环

执行循环：

```text
读取工作状态、Git 差异和依赖
  → 选取依赖已满足的最高优先级任务
  → 确认当前输入输出契约和模块边界
  → 实现一个可验收的功能增量
  → 运行受影响的测试与必要端到端验证
  → 发现问题就修复并复测
  → 留下版本、测试证据和下一步
  → 自动选择下一项
```

Phase 0 的现场盘点完成后，自动进入 Phase 1。必须先跑通 Phase 2 的遗忘闭环，再接入依赖它的真实集成。之后继续 Phase 3–8，不把“第一条闭环通过”当成项目全部交付。

阶段门是机器验证门，不是人工接力门。阶段出口未满足时不得标完成；不影响该失败点的独立模块可以继续开发，但不能将它们集成为已通过的发布候选。

## 4. 解耦要落实到代码，不只是目录名称

### 4.1 业务逻辑只有一份

Web、MCP、CC Adapter 是入口，不各自实现记忆、审批、计划或检索算法。按主文档的 Capability Registry 和领域服务调用同一份逻辑。

路由和工具处理器负责参数检查、认证上下文和返回格式；资源授权仍必须在业务执行层校验。不得相信模型在参数中自报的身份。

### 4.2 模块之间按契约调用

记忆、工作区、审批、原文、检索、日历、计划、身份、bootstrap、媒体及外部服务适配分别明确负责人和接口。默认不跨模块直接修改对方表或文件；跨域操作经服务接口或已定义事件协调。

日历读取源记录，不复制出第二套权威记忆。正式库和工作区保持物理独立；工作区不混入默认搜索、日历正式条目或开窗上下文。审批跨库发布继续采用原规格要求的幂等、版本检查和可恢复流程，不假装一次普通事务能覆盖所有副作用。

### 4.3 核心不依赖外部供应商

Siren、Superposition、扎西德勒、embedding provider、CC Host 通过适配层接入。缺少外部服务时，核心和契约测试可继续，但该项必须报告未真实联调。禁止把一个供应商的临时字段散落到多个核心模块。

沿用当前主文档的模块化单体方案；不为“解耦”擅自改成微服务群，也不新增必须付费的基础设施。

### 4.4 契约先行、变更可追踪

固定关键实体、输入输出 schema、错误码、事件、幂等与版本冲突规则后，再让相邻模块据此实现。明确已定的业务契约不能靠后写的模块随意改名、改语义来迁就自己。

工程性契约变更若不改变用户业务意图，可以自行决策，但必须补决策记录、调用方与兼容测试；涉及身份、审批、数据保留、隐私或用户已经明确的语义，不得擅自更改。

建立可执行的依赖边界检查或等效架构测试，不仅在最终报告里写“已解耦”。

## 5. 各阶段怎样不停顿推进

| 阶段 | 连续执行目标 | 不能冒充完成的地方 |
|---|---|---|
| 0 | 只读盘点本地源代码、生产映射、平台前置条件；固定依赖与基础契约 | 未读到本地信件/删除行为就照上游猜 |
| 1 | 身份、独立库、registry、审计、outbox、启动脚本、基础登录 | 工具人被授予主体身份或真实审批权 |
| 2 | 遗忘提案→任一授权主体审批→摘要检索→恢复，连同故障恢复 | 只显示摘要但后台仍搜旧正文/向量/缓存 |
| 3 | 原文、Hold、日期、关联、quotes、Home/Self/Diary/meaning | 用复述覆盖导入原文，或恢复逐字 quotes 标准 |
| 4 | 日历、相关计划、两套开窗策略、联系证据 | 自动扫描被当作乔生出现；加载全部计划 |
| 5 | 已核验的信件/删除适配；合成资料迁移与恢复演练 | 未经批准复制真实库、读取锁信或宣称生产迁移完成 |
| 6 | MCP/CC 实现与可执行的授权内联调 | 缺凭据仍写 verified_live；偷偷切换计费方式 |
| 7 | 范围内的生活能力、真实 API/UI、外部适配和契约测试 | mock 写入被算真实成功；擅自执行真实消息/通话 |
| 8 | 全量测试、E2E、审计式自查、修复、候选构建、交付报告 | 用单元测试数量代替验收覆盖，或自动部署生产 |

发现一个外部依赖阻塞时，只暂停依赖它的链路。不得因为 Siren 未接通就停止日历、媒体管理或核心测试；也不得因为这些模块完成就抹去 Siren 的真实阻塞。

Phase 9 生产切换仍不在本次自动执行范围。

## 6. 测试、检查与完成标准

每个功能至少记录：对应规格/验收 ID、实现位置、实际运行命令、结果、证据位置和适用的 commit。结果使用明确类别，不将“能编译”当成业务已完成。

保留 `not_started`、`tested_mock`、`verified_live`、`blocked` 等原规格状态的含义；本地真实功能可另记本地测试证据，但不能把 `tested_mock` 改称真实平台通过。建立规格 ID → 测试代码 → 执行证据的映射，不能只累计通过测试总数。

重点回归不得省略：

- GPT Chat/后台工具人无权审批正式记忆；Claude Chat 与 CC 对应同一个周家明；开发测试身份与线上身份严格隔离。
- 未批准草稿不能进入默认记忆、日历或开窗；批准前原桶不变，批准后仅批准版本的摘要参与检索。
- 遗忘旧正文、旧 meaning、向量、缓存及迟到索引任务不会偷偷恢复搜索命中；默认不自动展开旧正文。
- 重试不重复写入、双入口修改不静默覆盖、并发审批不重复生效、崩溃后能恢复一致状态。
- Chat 30 条真实消息与三天桶；CC 不自动塞原文；两边只读进行中和临近计划，并处理逾期未完成事项。
- 日历按事件日期显示；程序活动不能刷新真实联系时间。
- quotes 允许语义一致的复述；明确语义冲突才纠正，并保留修改记录。
- 信件/删除遵守本地核验行为；生产数据、锁信正文、密钥不进入测试输出或 Git。
- Web 页面刷新后数据仍在，导航和按钮确实工作；MCP 与 Web 的业务结果一致。

自动化检查按项目实现提供真实命令：格式/静态检查、类型检查、单元、契约、集成、E2E、构建、秘密扫描、依赖边界检查，以及主规格要求的权限/并发/故障恢复/迁移/备份测试。命令必须实际存在并执行，不只写进 README。

截图能证明页面显示状态，不能单独证明权限、持久化或后端业务正确。mock 适用于隔离测试，不适用于宣称真实服务已连接。

每个里程碑结束时可先提交当前功能，再切换审阅视角进行一次不改代码的检查，列出可验证的问题，然后修复并重跑测试。同一个模型的自查是额外检查，不得标注为林石见已经审计或独立第三方已验收。

不得删除失败用例、放宽断言、把错误改成成功、关掉必要功能、解除权限或只保留静态演示来制造全绿。测试确有错误时记录依据并改正，必须保留原业务验收意图。

## 7. 上下文管理和中断恢复

在项目仓库维护：

- `docs/PROGRESS.md`：做过什么、当前版本、通过与失败的测试。
- `docs/NEXT.md`：下一项具体工作、依赖、应运行的命令和注意点。
- `docs/BLOCKERS.md`：阻塞原因、已尝试措施、影响范围、需要什么条件。
- `docs/DECISIONS.md`：自己作出的可逆工程默认选择及理由，不写成用户原话。
- `docs/verification/`：脱敏后的运行证据，或指向不入 Git 的大型日志路径。

可另建立机器可读任务清单；由原规格生成，保留需求 ID 和原始预期。不能通过删任务让待办归零。

每个已验证增量留下小型、可追踪 commit，记录预存的用户修改，不把他人的未提交工作混进自己的提交。不得擅自 `reset --hard`、批量清理目录或覆盖用户修改。尚未完成的改动也要写入续跑记录，不伪造通过状态。

恢复会话时先读这些文件，再检查真实 Git 状态并运行基础 smoke test；记录与仓库冲突时，以可核验状态为依据修正进度，不从零重写。

只使用宿主实际提供且允许的压缩/续跑机制。不要杜撰“无限时长”参数，也不要关闭权限提示或绕过限制。当前环境不能自动续跑时，保存断点并如实说明；一份提示词不能保证绕过宿主的会话、时长、认证或调用限制。

中断不等于项目完成。最终总结不得因为窗口快满，就把未验证功能改成完成。

## 8. 额外额度与并行使用

可以充分使用用户现有开发额度进行实现、重跑、审阅与验证，不为了省 token 删减需求。额外额度优先用于失败复现、边界测试、重构后的全量回归、浏览器 E2E、文档与代码一致性检查。

不为了耗额度启动没有终点的循环。对同一失败反复出现时，改变诊断方式、缩小复现或记录外部阻塞；不要无限重复同一个失败命令。

子任务并行是可选方式，不是必需条件。只有宿主已支持且模块边界明确时，才允许并行；否则由单个执行者连续推进。

建议先由主执行者固定 schema、身份、审批与核心契约，再把不互相阻塞的模块分给独立工作区/分支。为每个子任务指定文件责任范围和接口版本。共享 schema、鉴权、迁移和依赖锁由主执行者协调；不得多路同时修改同一共享文件。

主执行者负责合并并运行集成/E2E。不同子任务各自通过，不等于合起来通过。并行失败时可以收回为串行，不改变验收标准。

## 9. 自主范围与真正需要人工的地方

普通可逆工程选择、范围内代码实现、合成资料测试、局部重构、缺失 schema 补齐、文档和新项目内 commit，可以自行推进。按原规格锁定依赖，不能自动购买服务、升级套餐或把现有额度改成另行计费的 API。

下列边界不因“连续执行”解除：

- 旧 Ombre 与其他项目的目录、服务、数据卷、端口、Tunnel 和生产入口不改。
- 取得、复制或使用真实数据快照仍按迁移手册授权；不得让模型为开发提前看锁信或全量私人聊天。
- 凭据、用户交互登录、计费方式或权限变更不能伪造；不收集无关凭据。
- 对真实 Siren/星星瓶/群聊等造成写入、发送、通话、唤醒或通知，须有对应明确授权或隔离测试目标。
- 自动唤醒默认关闭。测试用 fake clock 和合成接收方不能接到真实通知出口。
- Phase 9 的正式迁移切换、旧写入暂停和公网路由变化，仍须另行批准。

这些限制不妨碍先把实现、适配、受控测试和待联调步骤写完。缺条件的项逐一标明 blocked，然后继续其余授权内工作。

## 10. 什么时候可以停，以及怎样交付

允许结束当前连续执行的条件只有：

1. Phase 0–8 授权内目标已实现并按真实证据验证，生成发布候选；仍不自动上线。
2. 剩余工作都被真实外部条件、权限或关键规格冲突阻塞，且无独立可继续工作。逐项报告，不能写成“全项目完成”。
3. 用户主动暂停，或宿主终止/无法继续。保存断点，标明部分完成。

每阶段短报一次：完成什么、测试结果、阻塞、下一项。短报后继续，不问“还要继续吗”。

最终交付至少包含：候选 commit、实际启动命令、模块与能力覆盖、118 条原始验收用例对应证据、额外回归证据、真实联调与模拟状态、迁移演练结果、未解决问题、暂留功能、已确认未修改的生产边界、需另行批准的下一步。

只有无未通过的必需验收，且所有声称已接通的服务都有相应真实证据，才可写“满足开发候选验收条件”。部分模块完成、mock 全绿或仅构建成功，都不等于整套项目验收完成。部署与真实数据切换单独报告。

## 11. 可以直接贴到 GLM 的总指令

```text
执行 mariposa 完整工程包，并启用《05_连续执行模式.md》。

这是一项 Phase 0–8 的连续开发任务，不是只做第一阶段。
你在授权范围内自行拆解、实现、测试、修复、提交并自动进入下一项，
不要每阶段问我要不要继续，也不要停在计划、脚手架或静态页面。

先核对本地 Ombre，再完成遗忘提案→审批→仅摘要检索→恢复的完整闭环，
随后按依赖顺序继续其他模块，直到发布候选或只剩真实外部阻塞。

解耦必须有统一业务服务、固定契约、模块边界检查与集成测试；
不要让 Web/MCP/CC 各写一套逻辑。额度充足，优先用在实现和充分验证上，
但不要为了耗额度无休止循环，也不允许擅自改变计费方式。

每个可验证增量留下 commit、测试证据、PROGRESS/NEXT/BLOCKERS。
支持续跑就按宿主支持的方式接续；不支持就保存断点，不假装任务完成。

未联调标 blocked/tested_mock，不得假称 verified_live；
不允许用降低权限、删测试、关功能换取全绿。
旧生产、真实数据快照、真实外部写入和 Phase 9 切换仍遵守单独授权。
只要还有已授权且可推进的工作，就继续，不等待我逐关陪跑。
```

## 12. 参考与核验边界

本补充以当前用户的“让 GLM 一口气跑完”要求及 v1.0 工程包为依据，没有核验用户当前 GLM/ZCode 宿主的单轮时长、上下文长度或自动续跑能力。

长任务组织参考 Anthropic, *Effective harnesses for long-running agents*（2025-11-26；本次查阅 2026-09-21）：采用功能清单、增量开发、Git/进度记录及端到端验证。该文研究的是其测试环境，不构成 GLM 能无中断运行的保证。
